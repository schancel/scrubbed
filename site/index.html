scrubbed

A local-first text-sanitization CLI in D: mojibake/encoding repair, normalization, and opt-in mechanical HTML→Markdown conversion, run in parallel across an input document tree.

Source on GitHub README #!blag

What's actually working right now

  • A pluggable filter-registry pipeline with a CLI that walks an input directory tree and mirrors it to an output path, parallel across files via std.parallelism's TaskPool — real OS threads, not fibers.
  • Zero-copy input reads via std.mmfile.MmFile, atomic output replacement, and deterministic per-file cleanup.
  • Mojibake/encoding repair for the Latin-1/Windows-1252 scope, with a conservative badness scorer. Against the current ftfy JSON corpus it repairs all 39 passing cases mechanically reachable through those two encodings and preserves all 48 encoding-negative cases.
  • HTML entity decoding covering all 2,231 WHATWG named references, plus smart-quote and line-ending normalization filters.
  • An opt-in extract --format=markdown route that mechanically converts HTML to Markdown (no main-content/boilerplate selection — that's a harder problem this doesn't attempt yet).
  • A bounded four-class PII scanner exposed as a pure D API, with report/mask and an opt-in redact policy — not CLI-driven redaction or complete de-identification.
  • An exact-byte dedup overlay facade over the C01 shard API.
  • A deterministic character-n-gram language identifier (Cavnar & Trenkle-style rank distance — no embedded model, no network dependency) covering 11 Latin-script languages: English, Spanish, French, German, Portuguese, Italian, Dutch, Turkish, Vietnamese, Polish, and Indonesian. It abstains rather than guessing on input that's too short, uses an unsupported script, or is ambiguous/low-confidence, and its confidence score is explicitly relative and uncalibrated, not a probability. Like the PII scanner, it's a self-contained pure D API — not yet wired into any CLI, config, or pipeline stage.
  • A JSONL streaming mode (--input - --output -) that runs selected text fields through the same filter chain for corpus pipelines.
  • An opt-in error journal and local SQLite-backed manifest for tracking per-file failures and resuming interrupted local runs.

Why this exists, honestly

Inspired by ftfy (encoding repair) and trafilatura (web text extraction) — but this is not a drop-in replacement for either. ftfy's real value is years of tuned heuristics for telling corrupted text from fine text; scrubbed covers a conservative slice of that (Latin-1/CP1252) and says so. trafilatura does DOM-based main-content extraction with boilerplate removal; scrubbed's HTML→Markdown route is a bounded, mechanical converter, not a content-selection system.

Status

Phases 0–2 are usable within their documented scope. This is not yet a proven terabyte-scale engine, and the project is explicit in its own docs about what isn't covered yet — see TODO.md in the repo for the current, unvarnished list.

Usage

dub build --build=release
./scrubbed --list-filters
./scrubbed --input path/to/docs --output path/to/clean \
    --filters normalize-line-endings,strip-control
./scrubbed extract --input page.html --output page.md --format markdown
