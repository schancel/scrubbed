scrubbed

One native binary that turns raw scraped web pages into clean training/eval data — encoding repair, main-content extraction, and PII scanning in a single pass per document, plus dedup and language ID as separate stages on the same underlying pipeline. No interpreter, no intermediate files, no chain of separate tools.

Source on GitHub README #!blag

Why

Bad corpus cleaning quietly costs more than it looks like it does: mojibake nobody caught, nav/ad/footer boilerplate mixed into "content," PII nobody scrubbed, near-duplicate pages nobody deduped — none of it throws an error, it just degrades whatever gets trained on it. Doing this step correctly, and fast enough to run over a real corpus rather than a sample, is table stakes for everything downstream.

The problem

Most corpus-cleaning pipelines today are a chain of separate Python tools glued together with intermediate files: ftfy to fix encodings, trafilatura to pull the article out of the page, langdetect to tag the language, Presidio to find PII, a separate dedup pass — each one its own interpreter startup, its own read/write of the whole document, its own set of heap allocations and garbage collection sweeps. None of them were built to compose with each other, so both correctness and performance leak out at the seams between tools.

scrubbed replaces that chain with one native binary and one shared pipeline instead of five separate tools each with their own interpreter startup and intermediate files. clean-web-document bundles mojibake repair, HTML main-content extraction, and PII scanning into a single pass per document today; dedup and language ID run as separate stages on the same underlying machinery rather than in that same pass yet — see the usage examples below for exactly what's bundled versus separate right now. Where a case is covered, it's built and verified to match the reference tool's output, not just approximate it — see the numbers below. Coverage is still growing (more encodings, more scripts, more languages, more of the pipeline unified into one pass), but the bar for anything shipped is drop-in correctness on what it claims to cover.

Where this fits in a training pipeline

Building a corpus for pretraining or fine-tuning is usually four stages: collect raw pages, clean & curate them into usable text, package the result into training-ready shards, then train. scrubbed's job is the middle stage — the part that's normally a chain of separate Python tools today.

scrubbed hands off via plain JSONL (or its structured-chunk projection) to whatever tokenizer/shard-writer you already use — it doesn't tokenize or train. Collection is now a real shipped command too: scrubbed crawl is a local, multithreaded, resumable crawler (durable SQLite-backed frontier, bounded polite fetch, link discovery) — single-machine only, no distributed/sharded crawling yet. It writes raw pages only, no cleaning inline; run clean-web-document over its output as a separate pass, or point scrubbed straight at pages you already have.

The pipeline, one command

scrubbed clean-web-document --input page.html --output page.txt
scrubbed clean-web-document --input pages/ --output clean/ --threads 4

Repairs mojibake, extracts the article body out of the page (nav/ads/footers dropped), pulls out title/author/date/url, and scans the result for emails/phones/card numbers/IPv4 addresses — writing one metadata sidecar next to the output with both the extracted metadata and the PII audit in it, one process, one pass, parallel across a whole directory tree.

Verified against the tools it replaces

Every number below comes from benchmarks/external_comparator.d, runnable yourself against real pinned installs of each reference tool — not a claimed result.

39/39 + 48/48 vs. ftfy, encoding repair

Exact match on ftfy's own test corpus, within scrubbed's Latin-1/Windows-1252 scope: every corrupted case fixed, every clean case left untouched.

11/11 vs. langdetect, language ID

100% classification agreement on a real held-out run, across scrubbed's 17 supported languages.

21/21 vs. Presidio, PII detection

Exact parity with Presidio on every category: email, card, IP (5/5 each) and phone (6/6, including parenthesized numbers like "(415) 555-0199"). Zero false positives from scrubbed on any category.

18/20 pages vs. trafilatura, extraction

Precision 0.918 / recall 0.746 against trafilatura's own extraction as the reference (not authored ground truth — a cross-tool word-overlap comparison). The 2 pages that don't parse are a known, ticketed parser gap — see docs/html-main-content.md.

~146x whole pipeline vs. the equivalent Python chain, corpus-scale

scrubbed's clean-web-document vs. ftfy→trafilatura→langdetect→Presidio chained, over a 400-file corpus with the Python chain warm, measured as CPU time. Methodology and a smaller per-file comparison in examples/pipeline-benchmark.

~25x vs. ftfy alone, whole-process wall time

On a 131,072-line (5.9MB) repetitive mojibake file: 0.152–0.156s vs. ftfy's 3.698–4.076s. Whole-process timing including startup, exact output verified every run — one specific workload, not a general throughput claim. Per-tool timing for trafilatura/langdetect/Presidio individually isn't published yet, only the whole-pipeline number above and correctness per tool.

Also shipped

  • A four-class PII scanner (email/phone/card/IPv4) with report, mask, and opt-in redact modes, publishing a content-free audit record.
  • Exact-byte deduplication across a corpus.
  • A deterministic, model-free language identifier — no embedded model, no network call — reachable from the same generic pipeline as every other stage.
  • An opt-in per-document quality signal: order-0 token entropy plus compression ratio, for flagging degenerate/repetitive text.
  • HTML entity decoding (all 2,231 WHATWG named references), smart-quote and line-ending normalization, and a JSONL streaming mode for corpus pipelines that only need specific text fields touched.
  • Real parallelism across files (OS threads, not green threads), zero-copy input reads, atomic output writes, and an opt-in error journal/manifest for resuming interrupted runs.
  • A bounded WARC/1.1 reader (plain, gzip, and zstd-compressed) for reading existing archives.
  • scrubbed crawl: a local, multithreaded, resumable crawler — durable SQLite-backed frontier with permanent duplicate-rejection, bounded polite HTTP fetch via libcurl, HTML link discovery, real OS-thread concurrency with correct per-host throttling under concurrency. Single machine only; no distributed or sharded crawling. Kill it mid-run and it recovers cleanly on restart, no duplicate fetches.
  • Declared topical-tag extraction, a source-rights policy engine for permission/takedown decisions across derived artifacts, and structured chunking with stable, content-addressed chunk IDs for downstream corpus formats.

Status

Used today for local, single-machine corpus runs within the scope described above. Proven multi-terabyte-scale operation is still on the roadmap — see TODO.md in the repo for the current, specific list of what's next.

Roadmap

This section is direction, not a committed timeline or a shipped claim — only the numbers and features above are guaranteed to work today. It exists so people building on scrubbed can tell what's stable to depend on versus what's still being decided.

Near-term, the path to a first public release is ordered in docs/release-execution-plan.md: a canonical config/composition root, the complete built-in transform path, extraction/curation parity (dedup, similarity, PII, quality, language ID), then packaging. Direct S3 access, multi-machine distributed execution, and full parity with tools like Trafilatura, ftfy, Dolma, or DataTrove are explicitly deferred — useful later, not release blockers now.

Longer-term direction: the target shape (accepted, not yet built) is keeping scrubbed a bounded, single-machine tool at each of a few layers — crawl, transform/extract, and corpus-wide operations like dedup and clustering — and letting an existing distributed engine (Ray, Spark, Beam, DataTrove, etc.) chain and scale those across machines, rather than scrubbed building its own distributed job coordinator. Everything beyond that shape — exact timeline, which orchestrator integrations ship first — is still open (see open issues). Ingesting more document formats beyond HTML/WARC/plain text is in progress: PDF and DOCX both have a real, unwired extraction seam landed (evidence-only evaluation plus a minimal FFI/text-walker binding, no stage/CLI wiring yet), images/OCR remains evaluated but not adopted — see docs/document-adapters-evaluation.md.

How that's meant to reach petabyte scale without losing the numbers above: the unit an external orchestrator would hand to scrubbed is a whole corpus shard run through the complete fused pipeline in one process — not one call per stage. Unfusing into per-stage calls (extract, then write; read, then PII-scan, then write; ...) would reintroduce exactly the serialize/materialize overhead this page's benchmarks show scrubbed avoiding. Corpus-wide operations (dedup, near-duplicate clustering, decontamination) are meant to run as separate, explicit passes over small derived fingerprints/hashes computed once while the text is already hot in the fused pass — not over the full document text again — so a global pass across petabytes doesn't mean re-scanning petabytes of text. This is the accepted target shape, not yet built: see issue #338 for the full decision record.

The full, current, itemized list lives in TODO.md — that file, not this page, is the source of truth for what's done versus next.

Feedback wanted

If you're building or running a corpus-cleaning pipeline at a lab, a startup, or anywhere with real production constraints, I'd genuinely like to hear from you — especially about whether the roadmap direction above (a fused local pipeline, corpus-global operations as separate passes, orchestrated by whatever distributed system you already run) would actually embed into your stack, and where it wouldn't. A concrete gap — "this needs to emit format X," "this needs to run under constraint Y," "here's the part of our pipeline this could replace" — is more useful than general encouragement.

Open an issue, or comment directly on the open architecture proposals linked above.

Usage

macOS (Apple Silicon) and Linux (x86_64/aarch64), both CI-verified — Windows isn't supported yet. On Linux, PDF/llama.cpp-backed features are excluded from the build (evaluation-only, no verified Linux binaries yet — see #379); the core pipeline (encoding repair, extraction, PII, language ID, dedup) is unaffected. Requires the D toolchain to build from source — dub and the LDC compiler. No prebuilt binaries are published yet — packaging is on the roadmap above.

dub build --build=release

# Crawl a seed list locally, 4 workers, resumable if interrupted
./scrubbed crawl --seeds seeds.txt --corpus-dir ./crawled --db crawl.sqlite \
    --concurrency 4 --max-pages 200

# Then clean what you crawled (raw pages land under ./crawled/raw/)
./scrubbed clean-web-document --input ./crawled/raw --output ./clean --threads 4

# Or run the whole pipeline directly on pages you already have
./scrubbed clean-web-document --input page.html --output page.txt
./scrubbed clean-web-document --input pages/ --output clean/ --threads 4

# Just extract, in whichever shape you need
./scrubbed extract --input page.html --output page.md --format markdown
./scrubbed extract --input page.html --output page.tree.json --format tree-json

# Language ID as a standalone stage, reachable like any other
./scrubbed run --input page.txt --output page.out \
    --sidecar-output page.langid.json --stage langid=language-id-detect

# PII scan with an audit sidecar, no rewrite of the input --
# pii-four-class only annotates, so it needs document-metadata-publish
# chained after it as the actual terminal stage
./scrubbed run --input page.txt --output page.out \
    --sidecar-output page.document-metadata.json \
    --stage pii=pii-four-class --stage publish=document-metadata-publish

# Compose several stages by hand -- each --stage NAME=IMPLEMENTATION
# opens a stage; --filter tokens attach to whichever one opened last
./scrubbed run --input page.html --output page.out \
    --sidecar-output page.document-metadata.json \
    --stage clean=text-transform --filter fix-mojibake \
    --stage extract=html-main-content \
    --stage scan=pii-four-class \
    --stage publish=document-metadata-publish

# Or skip stages entirely: --filters is shorthand for one single
# implicit text-transform stage
./scrubbed run --input path/to/docs --output path/to/clean \
    --filters normalize-line-endings,strip-control
./scrubbed run --list-filters
./scrubbed --help

# Corpus pipelines: stream selected JSON fields through the same filters
./scrubbed run --input - --output - --jsonl-fields text,title \
    --dataset-namespace corpus-v1 --source-key shard-0001 \
    --max-jsonl-line-bytes 1048576 --max-jsonl-output-bytes 2097152 \
    --filters fix-mojibake \
    < input.jsonl > clean.jsonl
